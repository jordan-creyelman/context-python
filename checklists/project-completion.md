# Checklist de fin de projet

Pourquoi : vérifier que le projet répond au besoin et peut être repris facilement.

Appliquer uniquement les points correspondant aux notions étudiées et au périmètre du projet. Marquer les autres « non applicable » avec une courte raison.

## Comportement

- [ ] Le besoin et le résultat attendu sont clairs.
- [ ] Le cas nominal fonctionne.
- [ ] Les limites et entrées invalides importantes sont traitées.
- [ ] Les erreurs utiles sont compréhensibles.
- [ ] Les données de test sont fictives ou temporaires.

## Code

- [ ] Les noms sont explicites et en anglais.
- [ ] Les fonctions ont des responsabilités claires.
- [ ] Les conventions déjà étudiées sont appliquées.
- [ ] Les types et docstrings sont présents lorsque ces notions sont étudiées.
- [ ] Les modules ou classes ajoutés répondent à un besoin réel.
- [ ] Les traces temporaires et secrets sont absents.

## Vérification et documentation

- [ ] Les tests utiles passent lorsque les tests sont étudiés.
- [ ] Les commandes exécutées et leurs résultats sont notés.
- [ ] Le README explique comment lancer le projet.
- [ ] Les dépendances et limites connues sont documentées.
- [ ] Les décisions significatives sont expliquées.

## Git et apprentissage

- [ ] Le diff a été relu.
- [ ] Le commit contient uniquement les changements attendus.
- [ ] Les fichiers temporaires ne sont pas suivis.
- [ ] Le statut Git est vérifié après le commit.
- [ ] L'apprenant peut expliquer entrées, sorties et choix.
- [ ] La progression est mise à jour uniquement avec une preuve réelle.
